# Brainstorm and Design

Use this lifecycle workflow for open-ended goals, unclear architecture, or a material gameplay or product fork. Brainstorming is not mandatory ceremony: a well-specified implementation or repair should bypass this workflow and execute directly.

Explore feasible candidate concepts against verified Software Inc capabilities, distinguish engine constraints from creative inspiration, compare meaningful tradeoffs, and recommend the strongest supported direction when one is clearly better.

Ask for user input only when a material fork would lead to genuinely different gameplay, product scope, or acceptance criteria and cannot be responsibly resolved from the stated goal.

Return structured design findings, recommended decisions, assumptions, unresolved gaps, and proposed design-decision updates to the SIM orchestrator.

Do not dispatch peer specialists. Do not mutate canonical SIM session state directly. The orchestrator owns routing, final design selection, and committed state changes.
