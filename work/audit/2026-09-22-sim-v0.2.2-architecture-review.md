The core architectural direction survives review:

- `production/sim` remains the sole handwritten SIM runtime authority.
- `plugins/sim` is generated deterministic projection only.
- SIM exposes one public Skill / one public product identity.
- Software Inc Beta 1.8.42 remains the governed canonical target.
- Candidate-bound acceptance, independent validation and fail-closed editor-native behavior remain mandatory.
- The architecture is a hardening/deployment-surface evolution, not a product rewrite.

The review found design ambiguities that would have produced incorrect publication or certification semantics if implementation had started from the first draft. All findings below were corrected in the written spec before implementation planning.

## Reference implementations reviewed

### CodeMaestro

Current working repository pattern confirms:

- portable `plugin.json`;
- `.codex-plugin/plugin.json`;
- one public runtime Skill;
- `RUNTIME.json`;
- deterministic source-to-plugin projection;
- independent source-anchored validator;
- path inventory / file hashes / aggregate identity;
- exact-candidate marketplace installation using Git-subdir pinning.

The current marketplace pin points to a pre-existing materialized plugin commit rather than to the commit that writes the marketplace registration itself. This validates the S→P→M publication correction below.

### Evochia Operator

The dual-build architecture confirms:

- canonical internal domain contracts may remain unchanged;
- one public operator may project internal Skills as non-public modules;
- exact-byte projection is preferable to semantic build-time rewriting;
- source-anchored provenance and differential live acceptance are appropriate for a one-public-entrypoint projection.

## Findings and corrections

### AR-01 — Marketplace/source-commit self-reference

**Severity:** HIGH  
**Initial problem:** The first spec said the marketplace should pin the "exact certified source commit". A semantic source commit S cannot simultaneously contain a generated plugin candidate whose bytes are derived from S and also know the final commit SHA that materializes that candidate.

**Correction:** Publication now uses three explicit revisions:

```text
S = semantic source freeze
P = plugin projection/materialization commit generated from S
M = marketplace registration commit that pins P
```

Marketplace registration pins P, never S. P/M are not embedded into the candidate because that would reintroduce self-reference.

**Residual risk:** host marketplace metadata shape must still be revalidated at implementation/certification time.

---

### AR-02 — Candidate bytes conflated with source provenance

**Severity:** HIGH  
**Initial problem:** Candidate identity included `source_commit`. An unrelated repository/documentation commit could therefore appear to create a new behavioral candidate even when plugin bytes were identical.

**Correction:** The spec now separates:

- content identity;
- source provenance;
- publication provenance.

Behavioral certification binds to final candidate content bytes; source commit remains auditable provenance.

**Residual risk:** equivalence reuse is allowed only after the independent source/projection validator proves the candidate bytes are identical.

---

### AR-03 — Universal ZIP digest assumption

**Severity:** HIGH  
**Initial problem:** Every acceptance record required `candidate_bundle_sha256`, but a marketplace Git-subdir or local plugin installation may not have a ZIP transport.

**Correction:** `candidate_tree_sha256` is the transport-neutral candidate key. Installation evidence separately records transport-specific fields such as:

- marketplace projection commit;
- marketplace commit;
- plugin locator;
- ZIP hash when an actual ZIP exists.

**Residual risk:** the host may not expose installed content hashes. In that case exact installation provenance must bridge the validated candidate to the tested session; model behavior is never used to infer bytes.

---

### AR-04 — Exact target represented only by version string

**Severity:** HIGH  
**Initial problem:** `Beta 1.8.42` alone is insufficient as an immutable certification context.

**Correction:** Certification and acceptance bind to `exact_target_manifest_sha256`, derived from the resolved exact-target capture manifest.

**Residual risk:** a governed future target-evidence promotion creates a new certification context even if the human-readable version remains unchanged.

---

### AR-05 — New candidate could reuse old A01–A05 implicitly

**Severity:** HIGH  
**Initial problem:** The first draft correctly required fresh A06, but then stated that after A06 only A07–A12 execute. That left A01–A05 susceptible to accidental historical reuse.

**Correction:** v0.2.2 sequence is now:

```text
A06 first as blocker/canary
→ if PASS
→ fresh A01–A05 + fresh A07–A12
→ all A01–A12 PASS on the same candidate/context
```

Historical v0.2.0/v0.2.1 PASS results remain regression history only.

---

### AR-06 — Cross-surface gate was undefined

**Severity:** HIGH  
**Initial problem:** `G6 REQUIRED CROSS-SURFACE PASS` did not define which surfaces/cases were release-blocking.

**Correction:** A versioned `certification-profile.json` is introduced.

v0.2.2 Preview profile:

- ChatGPT: installation/resolver + A01–A12 required.
- Codex: installation/resolver + A01/A03/A09/A10/A12 required.
- ChatGPT Project: evidence may be collected but is non-blocking unless explicitly advertised by the release.

A required platform limitation is BLOCKED, never silently treated as PASS.

**Residual risk:** changing this profile requires a versioned architecture/certification-policy change.

---

### AR-07 — Aggregate hash recursion not defined

**Severity:** HIGH  
**Initial problem:** The first spec required an aggregate candidate hash while also placing that hash inside provenance contained by the candidate, without defining the self-reference boundary.

**Correction:** Two hashes now exist:

1. `semantic_aggregate_sha256` — over a frozen set of identity-bearing paths that excludes recursively defined provenance.
2. `candidate_tree_sha256` — independently computed over the final complete plugin tree and recorded externally in CI/certification evidence.

Behavioral certification uses the final tree hash.

---

### AR-08 — `@Sim` display name vs resolver key

**Severity:** MEDIUM  
**Initial problem:** The initial draft used `@Sim` as the machine entrypoint. The working CodeMaestro pattern uses a lowercase plugin/resolver identity while the UI renders the product display name.

**Correction:**

```text
machine resolver = @sim
display name     = SIM
display mention  = @Sim when the host renders it that way
```

Certification tests the actual installed resolver/mention and does not assume case-sensitive UI text.

---

### AR-09 — FINAL_ARTIFACT threshold was still under-specified

**Severity:** MEDIUM  
**Initial problem:** The draft stated that finalization depends on artifact family and requested claim but did not define the machine authority that decides the threshold.

**Correction:** Add `production/sim/manifests/finalization-policy.json`, mapping:

- artifact family;
- artifact surface;
- delivery mode;
- claim class;
- required checks;
- minimum V-level;
- blocking evidence states.

A final artifact may legitimately be V2 when a static-only deliverable is the strongest supported claim; `FINAL_ARTIFACT` does not imply V3+.

---

### AR-10 — Archive safety limits were qualitative only

**Severity:** MEDIUM  
**Initial problem:** "bounded expansion" had no explicit policy authority.

**Correction:** Add `archive-safety-policy.json`. Plan B must freeze concrete corpus-backed limits before GREEN implementation. Windows path normalization/case-insensitive collision handling is explicitly in scope.

---

### AR-11 — Stacked integration topology was ambiguous

**Severity:** MEDIUM  
**Initial problem:** The design branch is based on unmerged v0.2.1 remediation, but the first draft deferred PR targeting entirely.

**Correction:** v0.2.2 review PRs target `sim/v0.2.1-remediation` while that lineage is pending, so review shows only the v0.2.2 delta. After v0.2.1 integration, v0.2.2 is rebased/retargeted and reruns CI.

---

### AR-12 — Unrelated hardening could unnecessarily block plugin projection

**Severity:** MEDIUM  
**Initial problem:** A single global integrity gate could force legacy verifier/security work to complete before deterministic plugin projection even when there is no interface dependency.

**Correction:** Dependencies are now explicit:

- Plan A identity contracts precede final Plan C interfaces and Plan D.
- Plan C can proceed once consumed identity contracts are stable.
- Plan B symlink/archive safety must complete before A07.
- all Plan B release blockers must complete before G7.
- legacy v0.1 verifier repair remains mandatory for final release audit, but is not an artificial prerequisite for writing the plugin builder.

## Overengineering review

No architecture rewrite is warranted.

The following were explicitly rejected as unnecessary:

- moving canonical runtime to a new `runtime/sim` tree;
- turning each domain/lifecycle module into a public Skill;
- introducing an LLM-as-judge;
- making all repository tools bundled/executable;
- forcing App/MCP/API-key dependencies;
- redesigning the 18-file knowledge foundation;
- replacing Evidence Registry governance;
- coupling every hardening item into one monolithic implementation PR.

The additional manifests introduced by review are justified because each becomes a single machine authority required by an already-confirmed defect class:

- `certification-profile.json` — required-surface/case policy;
- `finalization-policy.json` — artifact-state evidence policy;
- `archive-safety-policy.json` — resource/ZIP safety policy.

## Remaining non-architecture verification

These are implementation/certification gates, not unresolved design defects:

1. verify current host plugin metadata/schema at implementation time;
2. implement Plan A–D only after owner approval and formal implementation plans;
3. independently verify generated plugin candidate;
4. materialize P and marketplace registration M;
5. install exact candidate;
6. execute fresh A06;
7. if A06 passes, execute fresh A01–A05 and A07–A12;
8. execute required Codex subset;
9. complete G7 final security/provenance/release audit;
10. publish only after explicit owner authorization.
