## Planning-review corrections integrated

The planning self-review found and corrected issues before implementation:

### PRV-01 — Session schema lacked finalization-policy inputs

Plan A initially required `artifact.family` and `claim_class` while the existing session schema rejects undeclared artifact fields.

Correction:
- Plan A Task 7 now modifies `schemas/sim-session.schema.json`.
- Exact family and claim-class enums are frozen.
- Session-policy compatibility gets explicit schema tests.

### PRV-02 — Package-validator plan used a non-existent API name

The current repository function is:

`validate_package_tree(root: Path, families: list[str]) -> list[str]`

Correction:
- preserve that API for compatibility;
- add `validate_package_tree_report` and `validation_coverage`;
- legacy callers still receive error strings.

### PRV-03 — Archive intake did not cap compressed input bytes

The forensic audit identified unbounded expansion; planning review additionally noticed current `hash_corpus.py` reads the entire archive with `path.read_bytes()` before expansion checks.

Correction:
- add `max_archive_bytes`;
- stat-size gate before full reads;
- stream top-level archive hashing;
- test compressed-size limits with low injected thresholds.

### PRV-04 — Candidate/source equivalence wording was too permissive

Because final candidate tree includes provenance containing S, selecting another S can change exact candidate bytes even when semantic runtime files are unchanged.

Correction:
- certified behavior remains attached to frozen S/P candidate tree;
- later repository HEAD commits do not mutate P;
- selecting another S requires new tree-hash comparison;
- behavioral evidence reuse only when final `candidate_tree_sha256` is independently identical.

### PRV-05 — Plan D contained execution placeholders

Initial Plan D contained values such as angle-bracket source/candidate identifiers.

Correction:
- all execution identifiers are derived through shell variables, Git refs, build reports, or evidence JSON;
- placeholder scan is now zero across all four plans.

### PRV-06 — Global certification was not explicitly wired into release verification

A ChatGPT-only acceptance check must not be sufficient for `PREVIEW_CERTIFIED` when Codex is release-blocking.

Correction:
- Plan D adds `sim-certification-report.schema.json`;
- `verify_sim_certification.py` recomputes per-surface certification;
- `verify_sim_release.py` must call global certification before accepting `PREVIEW_CERTIFIED`;
- a regression test requires rejection when ChatGPT passes but required Codex evidence is absent.

### PRV-07 — Derived certification report risked post-verification mutation

Correction:
- verifier-generated `certification-report.json` remains immutable;
- separate `release-readiness.json` references its SHA-256 and fresh G7 result.

### PRV-08 — Pre-merge install discoverability could vary by host

CodeMaestro PR #24 demonstrated successful exact-byte Chat/Codex installation/activation before merge.

Correction:
- marketplace M is preferred;
- supported exact-byte local/ZIP installation is an allowed pre-merge fallback;
- fallback must prove installed bytes match frozen P/candidate tree;
- no merge is performed merely to make the candidate discoverable.

## Dependency graph

Recommended implementation order:

```text
Plan A — integrity contracts
   ├── defines candidate-bound acceptance/state interfaces
   └── must precede final Plan C provenance interfaces and Plan D

Plan B — security hardening
   ├── may proceed after or alongside late Plan A work
   ├── symlink/archive portions must finish before A07
   └── all release-integrity portions must finish before G7

Plan C — deterministic @sim plugin
   ├── consumes stable Plan A identity contracts
   └── produces validated candidate tooling required by Plan D

Plan D — live certification
   └── starts only after exact candidate passes C/G2/G3 and case-specific B gates
```

For lowest coordination risk, execute sequentially A → B → C → D even though parts of B are technically parallelizable.

## Execution method recommendation

**Recommended: subagent-driven development.**

Reason:

- 37 implementation tasks across four plans;
- multiple security/provenance boundaries;
- several interfaces shared across plans;
- a shipped false certification or packaging escape would have higher cost than the extra review contexts.

Execution pattern:

1. fresh implementer per task;
2. RED evidence;
3. minimal GREEN;
4. focused + full suite;
5. fresh task reviewer;
6. advance only if task review passes;
7. whole-branch review at end of each Plan A/B/C;
8. live Plan D begins only after final whole-branch review.

Native execution remains possible, but provides less independent review before integration.

## Remaining execution-time uncertainties

These are deliberately not guessed in planning:

1. exact current host plugin metadata schema must be revalidated when Plan C executes;
2. exact ChatGPT installation transport available for a feature-branch M must be observed; exact-byte local/ZIP fallback is allowed;
3. Codex installation/resolver support must be actually exercised;
4. concrete host persistence/script capabilities remain observational evidence, not design assumptions;
5. branch protection/ruleset enforcement is a pre-merge governance action after release readiness, not part of implementation Plans A–D.
