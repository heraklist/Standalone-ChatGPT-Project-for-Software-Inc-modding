# SIM v0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first working `SIM — Software Inc Modding` Preview runtime on top of the v0.1.0 canonical evidence foundation, with explicit `@Sim` orchestration semantics, modular lifecycle/domain workflows, traceable generated references, deterministic validation/artifact tooling, behavioral evals, Preview release packaging, and live cross-surface acceptance.

**Architecture:** Keep the existing v0.1.0 Project-first knowledge/evidence pipeline authoritative and add `production/sim/` as a new downstream runtime/product source surface. One user-facing `@Sim` orchestrator owns a structured session and composes bounded lifecycle/domain workflow modules; deterministic Python tooling validates schemas, references, artifacts, security boundaries, evals, and releases, while all detailed Software Inc truth remains derived from the canonical evidence/knowledge layer.

**Tech Stack:** Python 3.11, pytest, jsonschema, Markdown/Agent Skills `SKILL.md`, JSON Schemas, deterministic ZIP/hash tooling, existing GitHub Actions workflows.

**Spec:** `docs/superpowers/specs/2026-09-02-sim-software-inc-modding-architecture-v0.2.md`

## Global Constraints

- Preserve Software Inc Mod Studio's full mission: research, brainstorm, design, create, edit, extend, repair, debug, migrate, validate, package, and verify mods.
- The user-facing entry point is explicit `@Sim`; automatic activation is not the primary UX contract.
- Desired thread persistence must be represented honestly: never claim host persistence the active surface does not provide.
- One central orchestrator owns session state, specialist sequencing, conflict resolution, security gates, and final synthesis.
- Internal specialists are silent by default and may not independently dispatch other specialists or directly mutate shared session state.
- High autonomy never overrides evidence discipline: autonomous, but never fabricate.
- Canonical Software Inc target remains `Beta 1.8.42` with `GENERATION_GRADE` evidence until a governed evidence promotion changes it.
- Existing `production/knowledge/`, `work/corpus/`, Evidence Registry, exact-target gates, and E01–E74 remain authoritative.
- SIM references are downstream generated/derived artifacts with complete source-path + source-hash + output-hash provenance; never maintain a second independent knowledge base.
- Default mutation is non-destructive: original user artifacts remain read-only baselines; work happens on copies.
- User-supplied executable code is untrusted and static-first; bundled verified SIM tooling is the only automatically executable tooling class.
- R3 destructive/public/external actions require explicit approval; implementation autonomy does not imply merge/publish/deploy autonomy.
- Artifact states remain `ARTIFACT_UNBUILT`, `CANDIDATE_ARTIFACT`, `FINAL_ARTIFACT`.
- Verification levels remain `V0 DESIGN_READY` through `V5 REGRESSION_VERIFIED`; no state may advance without real evidence.
- Verification-before-delivery is mandatory for every generated or modified artifact.
- Script execution is capability-adaptive; unavailable deterministic checks are reported as `NOT_EXECUTED`, never fabricated.
- Do not invent ChatGPT Plugin manifests, nested-skill runtime semantics, Software Inc filesystem schemas, APIs, or persistence capabilities.
- `v0.1.0` Project release tooling must remain reproducible and green while SIM is added.
- SIM ships Preview before Stable; Stable promotion requires automated gates plus live cross-surface acceptance.
- ModForge remains a separate product and must not constrain SIM's Software Inc engine truth.
- Use TDD for every executable/schema behavior change: RED → minimal GREEN → refactor, with fresh verification before completion claims.
