## 1. Purpose

SIM already has a governed Software Inc knowledge foundation, an explicit `@Sim` root Skill contract, lifecycle/domain specialists, deterministic repository tooling, exact-target Beta 1.8.42 evidence, Preview build tooling, and live ChatGPT acceptance evidence.

The two completed audits established that the remaining work is not a redesign of the modding system. The remaining work is to make the implementation enforce the architecture's existing truth and integrity promises mechanically, and to turn the existing upload-oriented SIM surface into a first-class installable `@Sim` plugin/Skill projection.

This design therefore has two inseparable goals:

1. **Integrity hardening:** no artifact, acceptance result, collision verdict, release state, or final-state claim may be promoted beyond the evidence attached to the exact candidate being evaluated.
2. **Plugin projection:** SIM must be installable and invokable as one public `@Sim` Skill using a deterministic, source-anchored, independently verifiable plugin package, following working patterns already proven in CodeMaestro and Evochia Operator.

The architecture does **not** add new mod families, invent new Software Inc loader semantics, or weaken the existing fail-closed Building/Blueprint rules.

---

## 2. Design intent and success definition

The user-facing product remains simple:

```text
@Sim <Software Inc modding task>
```

The internal implementation may use evidence registries, domain modules, lifecycle modules, deterministic validators, artifact builders, research, and compatibility logic, but the public product remains one identity and one entrypoint.

A successful v0.2.2 architecture must make the following statement true:

> Every externally meaningful SIM claim is bound to an exact source revision, exact plugin candidate, exact target environment, exact validation level, and inspectable evidence. No lower-level proof may be promoted into a stronger status by metadata alone.

Examples:

- repository-green does not mean live-certified;
- a generated ZIP does not mean load-verified;
- a PASS from candidate A cannot certify candidate B;
- a storage observation does not establish a loader path;
- a file extension does not establish an install contract;
- a manifest claim does not override independently computed bytes;
- a bundled tool does not count as executed;
- `FINAL_ARTIFACT` cannot exist without the required verification evidence.

## 3. Reference implementations reviewed

### 3.1 CodeMaestro

The current CodeMaestro repository provides a working plugin pattern with:

- `.agents/plugins/marketplace.json`;
- portable root `plugin.json`;
- compatibility manifest `.codex-plugin/plugin.json`;
- one public runtime Skill;
- `RUNTIME.json` declaring public entrypoint and runtime topology;
- deterministic source-to-plugin projection;
- exact source SHA binding;
- path inventory and file hashes;
- aggregate candidate identity;
- independent plugin validator;
- fail-closed checks for undeclared files, symlinks, unsafe paths, unexpected executable hooks, duplicate runtime sources, identity drift, projection byte drift, and forbidden dependency requirements;
- candidate certification tied to exact plugin bytes.

The architectural lesson adopted here is:

```text
canonical runtime source
        ↓ exact source SHA
projection policy
        ↓
deterministic builder
        ↓
plugin candidate
        ↓
independent source-anchored validator
        ↓
surface installation / behavioral certification
```

The generated plugin projection is not an independent semantic authority.

### 3.2 Evochia Operator

The Evochia Operator dual-build design demonstrates the complementary single-public-orchestrator pattern:

- many canonical internal domain Skills remain unchanged;
- a deployment projection exposes one public `@evochia-operator`;
- domain Skill bytes become internal module resources instead of public peer Skills;
- routing remains canonical;
- the root operator owns orchestration only;
- source bytes are read from an explicit Git commit;
- generated artifacts are reproducible;
- provenance records source path, projected path, transformation relation, source hash, projected hash, and full artifact inventory;
- validator checks actual Git objects rather than trusting the artifact's own manifest;
- live acceptance compares exact candidate artifacts and prevents a packaging projection from masquerading as a semantic rewrite.

The architectural lesson adopted here is:

> A single public Skill may safely compose many internal domain modules as long as canonical authority remains outside the generated projection and every projection relation is deterministic and independently verifiable.

### 3.3 SIM-specific decision

SIM combines the two patterns:

- **CodeMaestro** supplies the plugin/install/provenance/candidate-certification model.
- **Evochia Operator** supplies the single-public-entrypoint/internal-module projection model.
- **Existing SIM v0.2.1** remains authoritative for Software Inc evidence, routing, lifecycle behavior, domain behavior, verification vocabulary, fail-closed rules, and live A01–A12 acceptance semantics.

## 4. Architectural options considered

### Option A — Keep the current upload ZIP only

Continue using `build_sim_chatgpt_upload.py` as the final deployment artifact.

**Advantages**
- smallest code change;
- current tests already cover one-public-SKILL packaging;
- existing A01–A06 evidence lineage can continue.

**Disadvantages**
- no first-class plugin identity or marketplace registration;
- no deterministic plugin projection policy equivalent to CodeMaestro;
- current source-to-package transforms are not represented as a full plugin candidate contract;
- no source-anchored independent plugin validator;
- candidate identity and live certification remain easier to drift.

**Decision:** rejected as final architecture. It remains a migration/compatibility artifact only.

### Option B — Move all SIM runtime content into a new `runtime/sim` source tree

Mirror CodeMaestro exactly and make `runtime/sim` the new handwritten canonical runtime.

**Advantages**
- visually matches CodeMaestro;
- simple plugin projection path.

**Disadvantages**
- unnecessary semantic migration;
- duplicates or moves a mature `production/sim` authority surface;
- increases review blast radius;
- risks invalidating existing hashes/tests/history without functional benefit.

**Decision:** rejected. YAGNI.

### Option C — Deterministic plugin projection from existing `production/sim`

Keep `production/sim` as the sole handwritten SIM runtime authority and project it deterministically into `plugins/sim`.

**Advantages**
- preserves current source architecture;
- enables real plugin/Skill installation and `@Sim`;
- supports exact provenance and source anchoring;
- avoids duplicate handwritten runtime;
- allows current upload package to be retired gradually;
- cleanly separates source, projection, installation, and certification.

**Decision:** selected.

## 5. Canonical authority model

The repository contains several distinct authority surfaces. They must not collapse into one another.

### 5.1 Stable knowledge authority

`production/knowledge/` remains the canonical governed Software Inc knowledge foundation.

Its 18-file structure, Evidence Registry, exact-target claims, source roles, confidence, conflict metadata, and Beta 1.8.42 target evidence remain unchanged by this architecture except where an independently approved evidence update is required.

### 5.2 Runtime orchestration authority

`production/sim/` remains the sole handwritten runtime source for SIM behavior.

It owns:

- root `SKILL.md`;
- domain workflows;
- lifecycle workflows;
- runtime references;
- examples;
- SIM manifests;
- compatibility declarations;
- tool capability declarations.

### 5.3 Repository tooling authority

`tools/` owns deterministic repository-side validators/builders/analyzers.

A tool's presence in `tools/` does not mean it is packaged or executable on ChatGPT.

### 5.4 Generated plugin projection

`plugins/sim/` is generated output.

It must never become a second handwritten behavioral authority.

Manual semantic edits inside `plugins/sim/` are forbidden. Any required behavioral change is made in canonical source, then the candidate is regenerated.

### 5.5 Live evidence

`work/evidence/sim-acceptance/` stores observed certification evidence.

Live evidence is not canonical Software Inc game truth. It is evidence about a specific SIM candidate on a specific host/surface.

### 6.3 Marketplace registration and publication sequencing

Target:

`.agents/plugins/marketplace.json`

The marketplace source uses the working CodeMaestro pattern: a Git-subdirectory projection pinned to an exact commit that **already contains the generated plugin candidate**.

Because `.agents/plugins/marketplace.json` lives in the same repository as `plugins/sim`, publication is explicitly three-stage. The architecture distinguishes:

```text
S = semantic source commit
    contains canonical production/sim, policies, schemas, tooling and version inputs

P = projection/materialization commit
    parent/descendant of S
    adds the exact generated plugins/sim candidate built from S
    plugin subtree at P must independently validate against S

M = marketplace registration commit
    created after P
    updates .agents/plugins/marketplace.json to pin P
```

The marketplace must pin **P**, not S. Pinning S would be invalid when S does not yet contain the generated `plugins/sim` subtree. M is intentionally later than P and therefore avoids a self-referential commit-hash requirement.

Conceptual registration:

```text
marketplace name = sim-certification
display name     = SIM
plugin name      = sim
repository       = heraklist/Standalone-ChatGPT-Project-for-Software-Inc-modding
path             = ./plugins/sim
sha              = P
```

The exact current host metadata shape and installation/authentication fields must be revalidated at implementation time against the then-current supported plugin format. The working CodeMaestro marketplace is the current reference; unsupported metadata must not be invented.

Branch names or `main` never identify an installed candidate.

The generated plugin candidate does not embed P or M inside itself because doing so would create self-reference. Publication evidence outside the candidate records S, P, M, the candidate tree digest, marketplace locator, and installation result.

Changing any identity-bearing plugin byte creates a new candidate content identity and invalidates affected live certification. A marketplace-only commit that continues to pin the same exact P does not create new runtime bytes.

## 10. Deterministic plugin builder

New target tool:

`tools/build_sim_plugin.py`

The builder operates on an explicit full Git commit SHA.

Conceptual API:

```python
build_candidate(
    repo_root: Path,
    source_sha: str,
    output_root: Path,
) -> BuildResult
```

### 10.1 Source model

Candidate source bytes come from the exact selected Git commit.

Dirty working-tree state must not alter a build for source commit `S`.

The builder must reject:

- non-resolving source SHA;
- non-full/malformed source identity;
- unsafe projection paths;
- symlink source inputs;
- missing declared source files;
- source/policy inconsistency.

### 10.2 Reproducibility

For a fixed source commit and builder version:

```text
build(S) → candidate D1
build(S) → candidate D2

D1 paths == D2 paths
D1 bytes == D2 bytes
aggregate(D1) == aggregate(D2)
```

No timestamps, local filesystem mtimes, path separators, locale, or line-ending conversion may change candidate identity.

### 10.3 Builder authority

The builder may copy/remap declared bytes and generate declared metadata.

It may not:

- modify canonical Software Inc claims;
- rewrite domain instructions;
- infer new tool capabilities;
- invent host metadata;
- promote acceptance status;
- assign release certification.

## 12. Candidate identity and provenance context

The architecture separates **candidate content identity** from **source provenance**.

A Git source commit is essential traceability, but it is not itself the behavioral identity of the installed plugin. A later repository commit that changes unrelated documentation must not force a false claim that runtime bytes changed.

### 12.1 Content identities

Two deterministic hashes are used.

**Semantic aggregate SHA-256**

Computed over the declared identity-bearing runtime/plugin paths. It may be stored inside provenance because recursive provenance files are excluded from this aggregate.

**Candidate tree SHA-256**

Computed by the independent validator over the **final complete `plugins/sim` file tree**, including finalized provenance files. This value is recorded outside the candidate in CI/certification evidence and is not embedded back into the candidate, avoiding hash recursion.

Conceptually:

```text
semantic_aggregate_sha256
  = H(sorted(identity_path + NUL + sha256(file_bytes) + LF))

candidate_tree_sha256
  = H(sorted(all_final_plugin_path + NUL + sha256(file_bytes) + LF))
```

The exact identity-path set is frozen in the projection policy. At minimum, provenance files that contain the semantic aggregate itself are not inputs to that same semantic aggregate.

### 12.2 Certification identity

Live behavioral certification binds to:

```text
plugin_identity
plugin_version
candidate_tree_sha256
exact_target_manifest_sha256
surface
certification_protocol_version
```

`candidate_tree_sha256` is the transport-neutral candidate anchor.

### 12.3 Source provenance

Every candidate also records:

```text
source_repository
source_commit = S
projection_policy_sha256
builder_identity
semantic_aggregate_sha256
```

The projection/materialization commit P and marketplace registration commit M are publication evidence outside the candidate.

Repository HEAD may advance after source freeze without invalidating an already materialized candidate P. However, rebuilding the plugin from a different source commit S2 changes embedded source-provenance bytes unless the resulting final candidate tree is independently proven byte-identical. Therefore behavioral evidence is reusable only when `candidate_tree_sha256` is unchanged; a changed tree hash always creates a new behavioral candidate.

No behavioral evidence may float free of `candidate_tree_sha256`, exact-target evidence, surface, and protocol version.

## 13. Provenance model

Generated:

`plugins/sim/provenance/plugin_manifest.json`

Minimum contents:

```text
schema_version
source_repository
source_commit
builder_identity
projection_policy_sha256
plugin_identity
plugin_version
runtime_skill
public_skill_count
domain_count
lifecycle_count
path_inventory_file
file_hashes_file
semantic_aggregate_sha256
```

`path_inventory.json` lists every candidate path.

`file_hashes.json` lists every identity-bearing candidate file and its SHA-256. It does not include a self-hash or other recursively defined hash record. The independent validator separately computes the final complete `candidate_tree_sha256` over all finalized plugin files.

Inside the runtime projection, `manifests/runtime-provenance.json` records source-to-package relations:

```text
source_path
package_path
relation
source_sha256
package_sha256
```

The outer plugin provenance records source and semantic-projection identity.

The runtime provenance records per-file projection lineage.

The independent validator computes the final complete `candidate_tree_sha256`; that external digest is the behavioral candidate byte identity used by certification. Neither provenance layer is trusted without independent validation.

## 14. Integrity Hardening Workstream A — candidate-bound live acceptance

This workstream closes forensic findings INT-01 and INT-02.

### 14.1 Current defect

Current acceptance aggregation can select the latest result independently per case and therefore can combine A-cases from different candidate bundles.

The release verifier can also accept a report whose `surface_acceptance` and `release_status` were manually promoted while bundle bytes remain valid.

### 14.2 New acceptance record contract

Every live acceptance result A01–A12 must include a transport-neutral candidate identity:

```text
schema_version
case_id
surface
result
candidate_tree_sha256
semantic_aggregate_sha256
candidate_source_commit
plugin_version
exact_target_manifest_sha256
certification_protocol_version
installation_evidence_id
host_observation
evidence_refs
retest_of
recorded_at
```

Transport/install metadata is recorded separately under the referenced installation evidence. Depending on surface it may contain:

```text
transport = MARKETPLACE_GIT_SUBDIR | ZIP_UPLOAD | LOCAL_PLUGIN | OTHER_SUPPORTED
projection_commit = P                  # when Git-subdir installed
marketplace_commit = M                 # when marketplace registration is used
marketplace_name
plugin_locator
bundle_sha256                          # only when an actual bundle/ZIP transport exists
installed_candidate_tree_sha256
```

`bundle_sha256` is therefore optional and **must not** be the universal behavioral candidate key.

The current file-name/retest lineage may remain, but candidate content identity, target evidence identity, surface and protocol version are mandatory.

### 14.3 Aggregation rule

Acceptance is computed for one explicit candidate.

Conceptual interface:

```python
summarize_acceptance(
    evidence_dir,
    candidate_identity,
    surface,
) -> AcceptanceSummary
```

It must never silently select records for another candidate.

### 14.4 Candidate status

For one surface and one certification profile:

- records for a different `candidate_tree_sha256`, `exact_target_manifest_sha256`, surface, or protocol version are ignored for that candidate and can never be mixed into its result;
- any required case `FAIL` → `FAIL`;
- any required case `NOT_TESTED` → `INCOMPLETE`;
- any required case `PLATFORM_LIMITATION` → `INCOMPLETE` unless the versioned certification profile explicitly permits that limitation;
- all required cases `PASS` in the same certification context → `PASS`.

### 14.5 Existing historical records

Old A01–A06 evidence without complete new candidate identity remains historical evidence.

It must not be retroactively upgraded by guessing.

Where an old artifact digest is already explicitly known in the observation record, migration may preserve it as historical candidate identity.

Otherwise the record remains pre-v0.2.2 evidence and cannot certify the new candidate.

## 15. Integrity Hardening Workstream B — semantic release verification

The independent verifier must verify more than ZIP integrity.

### 15.1 SIM release statuses

Separate build state from certification state.

Allowed Preview states:

```text
PREVIEW_BUILD
PREVIEW_VALIDATED
PREVIEW_LIVE_INCOMPLETE
PREVIEW_LIVE_FAILED
PREVIEW_CERTIFIED
```

A release builder may create `PREVIEW_BUILD` or `PREVIEW_VALIDATED`.

Only a verifier that can resolve candidate-bound live evidence may produce or validate `PREVIEW_CERTIFIED`.

No metadata edit alone may promote a build.

### 15.2 Required consistency

`PREVIEW_CERTIFIED` requires:

- plugin candidate independently validates;
- exact target gate passes;
- required deterministic repository evals pass;
- required artifact/security checks pass;
- A01–A12 all PASS for the same candidate on required ChatGPT surface;
- compatibility matrix reflects observed state;
- known critical gaps are empty;
- no unresolved blocker required by certification policy.

### 15.3 Report verification

The verifier independently recomputes:

- candidate digest;
- per-file hashes;
- exact source binding;
- acceptance aggregation;
- release-status eligibility.

The report is an output of verification, not a source of truth.

Add a JSON Schema for the exact-target collision index.

```json
    }
```

### 16.2 End-to-end invariant

```text

→ analyzer
→ collision index
→ schema validation
→ repository exact-target validation
→ classify_identifier("Game")

```

A producer/consumer pair that each passes isolated unit tests but fails this path is not accepted.

- junction/reparse-point equivalents where detectable;

- absolute paths;
- `..` traversal;
- ambiguous normalized paths.

A file discovered through an in-workspace symlink is not an in-workspace file.

### 17.2 Archive expansion budget

Archive inspection receives explicit limits:

- maximum entry count;
- maximum total uncompressed bytes;
- maximum per-entry uncompressed bytes;
- maximum compression ratio;
- maximum nested archive depth;
- maximum cumulative nested expansion.

The limits are versioned in a machine-readable source policy:

`production/sim/manifests/archive-safety-policy.json`

No hidden/default library limit is accepted as policy. Plan B must select and justify concrete values using representative corpus/adversarial fixtures before the first GREEN implementation. Windows-target path ambiguity, normalized duplicate names and case-insensitive collisions are covered explicitly.

Limit violations are deterministic `BLOCKED_UNTRUSTED_ARCHIVE`, not best-effort continuation.

### 17.3 Static-first executable handling

The existing universal untrusted-content policy remains.

Bundled or uploaded scripts/binaries are not executed merely because they exist.

## 18. Integrity Hardening Workstream E — legacy release verifier repair

The v0.1 generation-grade bundle remains historical canonical foundation.

Its independent verifier must be corrected so that it proves actual packaged content integrity.

Required rule:

```text
for every file_sha256 entry:
  hash(actual ZIP entry bytes) == declared file_sha256
```

It must also ensure:

- no undeclared packaged file;
- no missing declared file;
- manifest identity consistency;
- external bundle digest consistency.

This hardening does not imply that the published v0.1.0 artifact is known to be corrupted. It repairs the verifier's proof strength.

## 19. Integrity Hardening Workstream F — artifact state machine

This closes STATE-01.

### 19.1 Canonical representations

Use one machine representation for verification levels.

Selected machine IDs:

```text
V0

V3

V5
```

Human labels remain display metadata:

```text
V0 DESIGN_READY
V1 ARTIFACT_GENERATED

V4 BEHAVIOR_VERIFIED

```

Schemas and Python helpers must consume the same machine IDs.

### 19.2 Final artifact evidence

`CANDIDATE_ARTIFACT → FINAL_ARTIFACT` requires explicit evidence.

Artifact completion and verification strength remain distinct. A `FINAL_ARTIFACT` may legitimately be only statically verified when the requested deliverable and family policy permit that, but the response must never imply V3+ behavior from V2 evidence.

The machine-readable authority for finalization is:

`production/sim/manifests/finalization-policy.json`

It maps at least:

```text
artifact family
artifact surface
delivery mode
claim class
required validation checks
minimum allowed verification level
blocking evidence states
```

The transition helper consumes the applicable policy plus actual evidence/state, not only old/new labels. No caller may hard-code a stronger or weaker finalization threshold independently.

## 20. Tool capability governance

The plugin contains only tools explicitly approved for bundling.

Current `validate_code_profile` remains an example, not an automatic template for every repository tool.

A tool may be bundled only when:

1. its purpose is stable;
2. security behavior is reviewed;
3. package path is declared;
4. projected bytes are source-bound;
5. host execution remains labeled accurately;
6. absence of execution produces `NOT_EXECUTED`;
7. the tool does not require unsupported external secrets or paid API state.

Repository tools not meeting those conditions remain repository-only.

Potential future bundled helpers such as TyD/SIPL validators, collision checks, mod-tree inspection, or ZIP building must first pass the hardening workstreams above.

## 21. Package-family verification ceilings

The architecture distinguishes:

```text
validator exists
≠
validator fully covers the artifact family
```

Every package-family validator declares a coverage ceiling.

Examples:

- Data/TyD: filesystem/static validation;
- SIPL: static syntax/boundary validation;
- Code: lexical/compiler-profile static validation unless real compiler/runtime evidence is available;
- Furniture/Materials/Localization: family-specific structural checks;
- Editor-native Building/Blueprint: fail closed unless target-version native/editor workflow is evidenced.

No generic function called `validate_mod_package` may imply complete validation for unsupported families.

## 22. Building / Blueprint constitutional boundary

The current v0.2.1 remediation is retained unchanged in principle.

For Building and Building Blueprint:

- `Building.tyd` is not a proven native loader representation;
- `.build` and `.xml` observations do not establish generic authoring/install semantics;
- cloud/storage paths do not establish install paths;
- Workshop metadata does not create a public loader contract;
- an authoring kit, release kit, filesystem scaffold, installer, validator wrapper, or human-readable substitute is still fabrication if the actual supported workflow is unavailable.

The correct blocked state remains `TOOLING_BLOCKED` / evidence-scoped equivalent.

Plugin packaging must not weaken this boundary.

## 23. ChatGPT and cross-surface certification

### 23.1 Certification context

Live tests run only on a candidate that has already passed deterministic plugin validation.

The certification context freezes:

```text
candidate_tree_sha256
semantic_aggregate_sha256
source commit S
projection commit P
plugin version
projection policy SHA
exact target manifest SHA
surface
certification protocol version
installation evidence
```

A ZIP/bundle SHA is recorded only when that transport exists.

The exact-target evidence anchor is the SHA-256 of the resolved Beta 1.8.42 capture manifest (or its future governed replacement), not only the human-readable string `Beta 1.8.42`.

### 23.2 Resolver naming

The machine resolver key follows the working plugin pattern and is lower-case:

```text
@sim
```

The UI/display name remains `SIM`; a supported surface may render the user-facing mention as `@Sim`. Certification tests resolver behavior through the actual installed mention/token rather than assuming case-sensitive display text.

### 23.3 ChatGPT installation gate

Before behavioral cases:

- install/upload succeeds from the exact P or exact uploaded candidate bytes;
- expected plugin identity is visible;
- exactly one public `SIM` Skill is exposed;
- no internal domain/lifecycle names appear as peer public Skills;
- installation evidence binds the observed session to `candidate_tree_sha256`;
- marketplace installs record the pinned P and registration M;
- ZIP/upload installs record the exact bundle hash when applicable.

If the host cannot expose the installed content digest directly, the installation record must preserve the exact transport/pin and prove that it corresponds to the validated candidate tree. No digest is inferred from model behavior.

### 23.4 Fresh A01–A12 sequence

Historical v0.2.0/v0.2.1 results remain regression history and do not certify the new v0.2.2 candidate.

A06 is executed **first** as the current blocker/canary. If A06 fails, full behavioral certification stops for that candidate.

If A06 passes, execute **all remaining cases on the same candidate**, including A01–A05 and A07–A12.

Therefore G5 requires a fresh same-context PASS for all twelve A-cases:

```text
A06 first
→ if PASS
→ A01–A05 + A07–A12
→ A01–A12 all PASS on one exact candidate/context
```

No historical A01–A05 PASS may be reused to complete G5 for new bytes.

### 23.5 Versioned certification profile

Add:

`production/sim/manifests/certification-profile.json`

For v0.2.2 Preview the default release profile is:

**ChatGPT**
- installation/resolver: required;
- A01–A12: required.

**Codex**
- installation/resolver: required because the plugin publishes a Codex-compatible manifest;
- behavioral subset: A01, A03, A09, A10, A12 required.

**ChatGPT Project**
- evidence may be collected;
- not release-blocking for v0.2.2 Preview unless this release explicitly advertises Project as a supported installation surface.

A required surface that is actually exercised and proves a platform limitation is `BLOCKED`, not PASS. Changing the required-surface profile is a versioned architecture/certification-policy change, not a run-time waiver.

A PASS on one surface is never copied to another.

## 24. Certification gates

The v0.2.2 release chain is:

```text
G0  ARCHITECTURE REVIEW PASS

G1  CORE INTEGRITY CONTRACTS PASS
    candidate-bound acceptance
    semantic release verification
    collision contract
    evidence-bound state machine

G2  DETERMINISTIC PLUGIN PROJECTION PASS

G3  INDEPENDENT PLUGIN VALIDATION PASS

G4  CHATGPT INSTALL / RESOLVER PASS

G5  CHATGPT A01-A12 BEHAVIOR PASS
    all twelve fresh on one exact certification context

G6  CODEX INSTALL / RESOLVER + REQUIRED SUBSET PASS
    A01, A03, A09, A10, A12

G7  FINAL SECURITY / PROVENANCE / RELEASE AUDIT PASS
    includes symlink/archive hardening,
    legacy verifier repair,
    raw/private artifact policy,
    final package/release checks

→ PREVIEW CERTIFIED

Preview observation period
→ Stable promotion review
→ STABLE RELEASE READY
```

No later gate can compensate for a failed earlier gate.

A candidate tree byte change after G4 invalidates affected G4+ evidence. Repository commits made after S do not invalidate the frozen P candidate by themselves; certification continues to reference S/P. If a different S is selected and rebuilt, behavioral evidence is reusable only when the final `candidate_tree_sha256` is independently proven identical.

Security work required to execute a particular live case must be complete before that case runs. In particular, archive/symlink hardening is mandatory before A07.

## 27. Testing architecture

Tests are organized by property, not merely by file.

### 27.1 Deterministic projection

Must prove:

- two builds from same source are byte-identical;
- dirty worktree does not alter source-commit build;
- source byte drift is detected;
- second public Skill is rejected;
- undeclared file rejected;
- symlink rejected;
- unsafe path rejected;
- executable hook rejected;
- metadata identity drift rejected.

### 27.2 Acceptance integrity

Must prove:

- mixed candidate A-cases never aggregate to PASS;
- same bytes with different transport metadata remain the same behavioral candidate;
- different candidate tree bytes never share behavioral certification;
- missing candidate identity fails closed;
- malformed retest chain fails closed;
- duplicate terminal retests fail closed;
- `PREVIEW_CERTIFIED` cannot validate with A06 FAIL;
- manually edited release status cannot override evidence.

### 27.3 Collision integrity

Must prove real producer-to-consumer compatibility.

### 27.4 Artifact security

Must prove:

- symlink file exfiltration rejected;
- traversal rejected;
- duplicate ZIP member rejected;
- expansion budget enforced;
- nested archive budget enforced.

### 27.5 Legacy release integrity

Must prove tampering any packed knowledge file causes independent verifier failure even if outer bundle hash/report is edited.

### 27.6 State transitions

Must prove no artifact or V-level promotion without its exact evidence requirement.

### 27.7 Existing regression suites

Existing E01–E74 and S001+ remain mandatory.

The new tests do not replace live acceptance.

## 33. Architecture invariants

2. One public Skill: `sim`.

7. Live evidence is exact-candidate-bound.
8. No mixed-candidate acceptance.
9. Report metadata cannot override evidence.
10. Builder and validator are independently implemented where meaningful.
11. Validation checks actual source and candidate bytes.
12. No symlink/path escape.
13. Archive expansion is bounded.
14. Collision producer and consumer share one schema.
15. Final artifact status requires evidence.
16. Bundled does not mean executed.
17. Static verification does not mean runtime verification.
18. ChatGPT PASS does not mean Codex PASS.
19. Software Inc storage observation does not mean loader/install contract.
20. Building/Blueprint ambiguity fails closed.
21. Existing E01–E74 and S001+ remain regression gates.
22. A06 remains FAIL until a fresh exact-candidate live retest passes.
23. No release or merge is implied by a green repository build.
24. Candidate tree byte change invalidates affected behavioral certification; repository HEAD may advance while the certified S/P remain frozen, but selecting a new S requires candidate-tree equivalence proof before any behavioral evidence reuse.
25. No hidden chain-of-thought is required in evidence records.
