# SIM v0.2.3 Private Personal Plugin Architecture Design

Date: 2026-09-24  
Branch: `sim/v0.2.3-private-personal-plugin-architecture`  
Baseline: `sim/v0.2.2-plugin-manifest-remediation@8a8ea60a38aa01271b3ff2578e2dcfb82bed1efb`  
Supersedes as forward architecture: the v0.2.2 local-marketplace-centric certification target.  
Implementation status: **NOT AUTHORIZED — architecture/spec review only**

## 1. Purpose

SIM v0.2.3-preview changes the deployment and certification architecture of SIM without redesigning the SIM behavioral core.

The product goal is:

> SIM is a native, skills-only, USER-scoped, PRIVATE OpenAI personal plugin whose canonical source remains in GitHub, whose deployable package is deterministic and independently verifiable, and whose release is considered usable only after the exact private plugin release resolves and passes required live acceptance in ChatGPT Web normal Chat, ChatGPT Desktop, and Codex.

The design intentionally separates:

1. canonical source;
2. deterministic plugin projection;
3. independent static validation;
4. deterministic distribution archive;
5. OpenAI private personal-plugin release;
6. surface resolver verification;
7. behavioral certification.

This prevents local marketplace behavior, repository CI, or a package that merely looks correct from being mistaken for proof that the user-facing personal plugin actually works.

## 2. User requirements

The design is driven by these fixed requirements:

- SIM remains **private/personal**, for the owner only.
- SIM is **not** published to the public Plugins Directory.
- SIM is **not** implemented as or migrated from a Custom GPT.
- SIM must work from **ChatGPT Web normal Chat**, not only Work mode.
- SIM must also work from ChatGPT Desktop and Codex.
- GitHub remains the canonical engineering source and audit history.
- The plugin remains **skills-only** unless a future capability genuinely requires server-backed MCP behavior.
- Local/repository marketplace installation remains available for development and diagnostics, but it is not the final production identity.
- Behavioral evidence is bound to the exact candidate and exact platform release; old acceptance results are not inherited across candidate/release/protocol changes.
- No merge, Stable promotion, public publication, branch deletion, or destructive history rewrite is part of this architecture phase.

## 3. Non-goals

v0.2.3 does **not**:

- redesign SIM's domain model;
- replace the canonical Beta 1.8.42 evidence model;
- convert internal domain/lifecycle modules into public skills;
- add MCP solely to obtain plugin identity;
- add a public marketplace submission;
- add a workspace-scoped plugin as a substitute for the required USER-scoped plugin;
- relax the Building/Blueprint fail-closed contract;
- reinterpret prior failed or blocked certification evidence as PASS;
- make local marketplace success sufficient for production release.

## 4. Existing architecture retained

The following v0.2.2 architectural decisions remain authoritative:

### 4.1 One handwritten runtime authority

`production/sim/**` remains the only handwritten SIM runtime authority.

Generated plugin projections are derived artifacts and must never become a second semantic source of truth.

### 4.2 One public skill

The plugin exposes exactly one public SIM skill:

`skills/sim/SKILL.md`

Internal domain and lifecycle modules remain non-public references projected beneath the SIM skill.

### 4.3 Exact target

The default canonical Software Inc target remains:

`Beta 1.8.42`

Certification remains cryptographically bound to the exact-target capture manifest rather than only to a human-readable version string.

### 4.4 Risk and verification models

The existing contracts remain:

- R0 READ
- R1 WORKSPACE_WRITE
- R2 EXTERNAL_REVERSIBLE
- R3 EXTERNAL_DESTRUCTIVE_OR_PUBLIC

and:

- V0 DESIGN_READY
- V1 ARTIFACT_GENERATED
- V2 STATICALLY_REVIEWED
- V3 LOAD_OR_NATIVE_OPEN_VERIFIED
- V4 BEHAVIOR_VERIFIED
- V5 REGRESSION_VERIFIED

### 4.5 Building/Blueprint fail-closed behavior

The P0 Building/Blueprint preflight remains mandatory.

No local, web, repository, storage, Workshop, or export observation may be promoted into a public standalone loader/install contract without target-version evidence.

A missing native authoring/export capability remains:

`TOOLING_BLOCKED — native Building/Blueprint authoring/export evidence required.`

The v0.2.3 distribution redesign must not weaken this behavior.

## 6. Identity model

v0.2.3 replaces the local-marketplace-focused S→P→M release model with a platform-release model.

### 6.1 Identities

- **S5** — semantic source freeze.
- **P5** — deterministic plugin candidate tree derived from S5.
- **B5** — deterministic distribution archive containing exactly P5 as one plugin.
- **O5** — OpenAI private personal-plugin release created from B5.
- **C5** — certification context for O5 and its exact P5 identity.
- **M5** — optional local/repository marketplace registration used only for development and diagnostics.

### 6.2 Required chain

```text
S5
  -> exact deterministic projection
P5
  -> deterministic one-plugin archive
B5
  -> Plugin Creator create/update
O5
  -> retrieve platform release
platform release tree
  == P5
  -> live resolver and behavioral certification
C5
```

### 6.3 Production identity

The production user-facing identity is the OpenAI personal plugin:

- `plugin_id`
- `release_id`
- `current_release_id`
- `scope = USER`
- `discoverability = PRIVATE`

The local marketplace name and marketplace commit are not production identity fields.

## 7. Version authority

The repository currently contains duplicated manual version declarations. v0.2.3 removes this class of drift.

### 7.1 Canonical authority

`production/sim/manifests/sim-manifest.json`

is the single semantic version authority.

For this generation its version is:

`0.2.3-preview`

### 7.2 Consumers

The following are generated from or strictly verified against that authority:

- root `plugin.json`;
- `.codex-plugin/plugin.json`;
- deterministic distribution report;
- certification context/report;
- release evidence.

### 7.3 SKILL frontmatter

`production/sim/SKILL.md` must no longer contain a handwritten `metadata.version`.

The skill keeps only frontmatter required for the skill interface and any metadata that has a distinct, non-duplicative purpose.

This prevents `SKILL.md` from becoming an independent version authority.

## 8. Canonical plugin manifest

The root `plugin.json` becomes the canonical portable plugin identity and the canonical OpenAI presentation source.

It must contain:

- Agent Plugins schema declaration;
- `name = sim`;
- canonical version;
- portable description;
- repository/author metadata when supported by the pinned schema;
- `extensions.com.openai` presentation metadata when supported by the pinned schema.

The OpenAI interface should carry:

- display name: SIM;
- short description;
- long description;
- developer name;
- Developer Tools category or equivalent current supported category;
- declared capabilities;
- three starter/default prompts covering:
  1. create a Software Inc mod;
  2. inspect/repair an existing mod;
  3. diagnose a mod that does not load or behave correctly.

The exact field names are frozen only after validation against the vendored official Agent Plugins schema used by the implementation.

## 9. Compatibility manifest

`.codex-plugin/plugin.json` remains a compatibility fallback during v0.2.3.

It must:

- use the same plugin name and version as the canonical root manifest;
- point to `./skills/`;
- contain only compatibility/interface fields supported by the current compatibility contract;
- never override the semantic identity of the root manifest.

The file is retained rather than removed because:

1. Codex compatibility remains an explicit target;
2. Plugin Creator update semantics do not support arbitrary deletion of omitted files;
3. v0.2.3 should not introduce unnecessary path-set shrinkage before the personal-plugin lifecycle is proven.

## 10. Official schema validation

Internal builder/validator agreement is not sufficient proof of platform compatibility.

The validation pipeline becomes three-layered:

1. deterministic builder;
2. independent source-anchored internal validator;
3. official Agent Plugins schema validation.

### 10.1 Vendored schema

The repository stores a pinned schema under:

`schemas/vendor/agent-plugins/1.0.0/plugin.schema.json`

and records a checksum in:

`schemas/vendor/agent-plugins/1.0.0/SHA256SUM`

CI validates the schema checksum before using it.

### 10.2 Network independence

Normal deterministic CI does not fetch the schema at runtime.

A future explicit governance task may update the vendored schema, but a remote mutable schema must not silently change release results.

## 11. Deterministic distribution archive

A first-class plugin distribution archive is introduced.

Requirements:

- archive root is the plugin root;
- exactly one plugin is present;
- no outer version/name wrapper directory;
- archive path set equals the validated P5 path set;
- no undeclared files;
- no symlinks/reparse points/special files;
- deterministic member order;
- deterministic timestamps/permissions/compression settings;
- bundle SHA-256 recorded externally;
- archive can be reconstructed byte-identically from the same S5/P5 inputs.

The archive becomes B5 and is the only artifact supplied to Plugin Creator.

## 12. Plugin Creator production transport

### 12.1 Creation

For first production registration, the system uses the personal-plugin creation capability with:

- one validated archive B5;
- exactly one plugin;
- personal account context;
- required resulting scope `USER`;
- required resulting discoverability `PRIVATE`.

Creation is not considered certification.

A successful create response only proves that the platform accepted the archive and created a release object.

### 12.2 Verification after creation

After creation:

1. record `plugin_id`, `release_id`, `current_release_id`;
2. retrieve the current plugin source/archive from Plugin Creator;
3. reconstruct the platform release tree;
4. independently compare it with P5;
5. record `platform_release_tree_sha256`.

Required invariant:

`platform_release_tree_sha256 == candidate_tree_sha256`

If this invariant fails, certification stops.

### 12.3 Workspace fallback is forbidden

If the active account context cannot create a USER-scoped personal plugin, the result is a platform/deployment blocker.

The process must not silently substitute a WORKSPACE-scoped plugin because USER/PRIVATE is part of the product requirement.

## 13. Personal-plugin update semantics

Plugin Creator updates overlay uploaded files on the existing release and do not provide general deletion semantics.

Therefore v0.2.3 defines:

### 13.1 Same plugin ID update allowed

An existing `plugin_id` may be updated only when:

- identity remains `sim`;
- version advances;
- required files are replaced or added;
- the desired path set does not require removal of an existing path.

### 13.2 Path removal or rename

If a release requires path deletion or a rename that semantically requires deletion:

- stop the update;
- mark the update path as `BLOCKED_BY_PLATFORM_UPDATE_SEMANTICS`;
- require an explicit architecture/governance decision before creating a replacement plugin identity.

No stale file is knowingly left in the private plugin merely to keep an old identity.

## 14. Local/repository marketplace role

The local marketplace remains useful but is demoted from production distribution to development transport.

Allowed uses:

- candidate discovery diagnostics;
- local/desktop/Codex installation experiments;
- comparison against the personal-plugin release;
- pre-platform packaging tests.

It may not satisfy a production certification gate for:

- ChatGPT Web normal Chat;
- personal plugin registration;
- personal plugin release identity;
- personal plugin behavioral acceptance.

Marketplace evidence remains transport-specific historical evidence.

## 15. Certification protocol v3

The existing `sim-live-v2` profile is replaced by a versioned `sim-live-v3` protocol.

### 15.1 Required surfaces

Release-blocking:

- `CHATGPT_WEB_NORMAL_CHAT`
- `CHATGPT_DESKTOP_NORMAL_CHAT`
- `CODEX`

Supplementary/non-blocking unless a future approved profile changes this:

- `CHATGPT_WORK`
- `LOCAL_MARKETPLACE`

### 15.2 Surface isolation

A PASS on one surface does not imply PASS on another.

Examples:

- Web Work PASS does not satisfy Web normal Chat.
- Local marketplace resolver PASS does not satisfy personal-plugin resolver PASS.
- Desktop PASS does not satisfy Web normal Chat.

### 15.3 Transport isolation

Certification context includes both surface and transport.

The production certification transport is:

`OPENAI_PERSONAL_PLUGIN`

Local marketplace results never satisfy production transport requirements.

## 16. Installation evidence v2

The installation evidence schema becomes transport-aware.

### 16.1 Common fields

All records require:

- schema version;
- evidence ID;
- surface ID;
- result;
- candidate tree SHA-256;
- semantic aggregate SHA-256;
- source commit;
- plugin version;
- exact-target manifest SHA-256;
- certification protocol version;
- transport;
- recorded timestamp.

### 16.2 LOCAL_MARKETPLACE fields

When transport is `LOCAL_MARKETPLACE` or `MARKETPLACE_GIT_SUBDIR`, require:

- projection commit;
- marketplace commit;
- marketplace name;
- plugin locator.

The verifier independently proves:

- M pins P;
- P provenance pins S;
- P tree equals the declared candidate tree.

### 16.3 OPENAI_PERSONAL_PLUGIN fields

When transport is `OPENAI_PERSONAL_PLUGIN`, require:

- `plugin_id`;
- `release_id`;
- `current_release_id`;
- `scope = USER`;
- `discoverability = PRIVATE`;
- distribution bundle SHA-256;
- platform release tree SHA-256.

The verifier independently checks equality with P5.

## 17. Compatibility matrix redesign

The compatibility matrix becomes observational and surface-specific.

Each matrix record contains:

- surface;
- transport;
- discovery state;
- installation state;
- resolver activation state;
- thread persistence state;
- script execution state;
- artifact creation state;
- last verified plugin release ID;
- observation status.

This replaces broad claims such as:

`ChatGPT explicit_invocation = SUPPORTED`

with specific facts such as:

```text
surface: CHATGPT_WEB_NORMAL_CHAT
transport: LOCAL_MARKETPLACE
discovery: PASS
resolver_activation: BLOCKED
```

and separately:

```text
surface: CHATGPT_WEB_NORMAL_CHAT
transport: OPENAI_PERSONAL_PLUGIN
resolver_activation: PASS
release_id: <recorded exact release ID>
```

The implementation must use a real release ID in evidence; no placeholder is permitted.

## 18. Behavioral certification sequence

The exact production release must pass gates in order.

### G0 — Architecture approved

This design and its implementation plan are approved.

### G1 — Source freeze

Freeze S5.

### G2 — Deterministic candidate

Build P5 twice and prove identical tree and semantic identities.

### G3 — Independent internal validation

Validate P5 from S5 without importing builder implementation.

### G4 — Official schema validation

Validate root `plugin.json` against the pinned official Agent Plugins schema.

### G5 — Distribution bundle

Build deterministic B5 and independently prove B5 contains exactly P5.

### G6 — Private personal-plugin release

Create or validly update the USER/PRIVATE OpenAI personal plugin and record O5.

### G7 — Platform byte verification

Retrieve O5 and prove the platform release tree equals P5.

### G8 — Web normal Chat resolver

Using O5, prove explicit plugin selection/invocation resolves in ChatGPT Web normal Chat.

Unavailable support is `PLATFORM_LIMITATION/BLOCKED`, never PASS.

### G9 — A06 canary

Run fresh A06 first on O5.

Any A06 FAIL stops the candidate.

### G10 — Remaining Web acceptance

Only after A06 PASS, run fresh:

- A01–A05
- A07–A12

on the same O5 release and certification context.

### G11 — Desktop acceptance

Execute the required Desktop normal Chat installation/resolver and behavioral subset defined by the v3 profile.

### G12 — Codex acceptance

Execute fresh:

- A01
- A03
- A09
- A10
- A12

against the same P5/O5 identity where the surface supports the private plugin.

### G13 — Final security/provenance audit

Recompute:

- source/candidate/bundle/platform identities;
- schema validation;
- path inventory;
- security findings;
- evidence-chain uniqueness;
- required surface status;
- release state.

### G14 — Certification state

Only if all release-blocking gates PASS:

`PRIVATE_PLUGIN_CERTIFIED`

## 19. Evidence inheritance rules

Live evidence is non-inheritable when any of the following changes:

- candidate tree SHA-256;
- personal plugin release ID;
- certification protocol version;
- exact-target manifest SHA-256;
- required surface identity;
- production transport.

Prior records remain immutable historical evidence.

A retest may supersede an earlier record only within the same certification context and must explicitly reference the prior record.

## 20. Release-state model

The ambiguous generic `PREVIEW_CERTIFIED` state is replaced for the plugin lifecycle by:

- `SOURCE_VALIDATED`
- `PLUGIN_CANDIDATE_VALIDATED`
- `PLUGIN_BUNDLE_VALIDATED`
- `PERSONAL_PLUGIN_CREATED`
- `PERSONAL_PLUGIN_BYTES_VERIFIED`
- `WEB_RESOLVER_VERIFIED`
- `PRIVATE_PLUGIN_LIVE_INCOMPLETE`
- `PRIVATE_PLUGIN_LIVE_FAILED`
- `PRIVATE_PLUGIN_CERTIFIED`

A source/runtime ZIP may remain a useful engineering artifact, but it cannot inherit `PRIVATE_PLUGIN_CERTIFIED` merely because a different plugin artifact passed live certification.

## 21. Archive intake enforcement

The existing archive safety policy remains authoritative and gains a bundled deterministic inspector.

New helper responsibility:

`tools/inspect_archive.py`

It must statically reject or report:

- absolute paths;
- traversal segments;
- ambiguous backslash paths;
- symlink/reparse/special-file abuse where detectable;
- duplicate paths;
- Windows casefold collisions;
- entry-count limit violations;
- compressed-size limit violations;
- uncompressed-size limit violations;
- per-entry size violations;
- compression-ratio violations;
- nested archive depth/cumulative-limit violations.

It must produce structured JSON suitable for evidence and must not require unsafe extraction before the safety decision.

## 22. Tool capability model

`production/sim/manifests/tool-capabilities.json` becomes surface-complete.

Explicit surfaces:

- `CHATGPT_WEB_NORMAL_CHAT`
- `CHATGPT_DESKTOP_NORMAL_CHAT`
- `CHATGPT_WORK`
- `CODEX`
- `REPOSITORY_CI`

Each tool declares:

- bundled: true/false;
- execution: SUPPORTED/CAPABILITY_DEPENDENT/UNAVAILABLE;
- fallback;
- verification ceiling.

Bundling a Python file is never treated as execution evidence.

## 23. CI architecture

CI has two distinct concepts.

### 23.1 HEAD reproducibility

Every PR/push may build the current HEAD candidate twice to detect deterministic-build regressions.

This answers:

> Is the code at this HEAD reproducible?

### 23.2 Frozen certification candidate

Certification verification uses the explicitly frozen S5/P5/B5/O5 identities.

This answers:

> Is the exact candidate/release under certification still valid?

CI naming and evidence must make these two purposes impossible to confuse.

- current certification state;

## 26. Security boundaries

The v0.2.3 distribution work preserves:

- uploaded/external content as untrusted data;
- no instruction following from repository/archive payloads;
- static-first handling of executable content;
- no secret/API-key requirement in plugin package;
- no mandatory paid external service;
- no undeclared MCP/app dependency;
- no silent path traversal or special-file acceptance;
- no fabricated host capability.

Plugin Creator responses and retrieved plugin archives are treated as deployment evidence, not as instructions.

## 27. Failure handling

### 27.1 Static validation failure

Stop before Plugin Creator.

### 27.2 Plugin Creator creation failure

Record deployment failure and stop. Do not substitute public or workspace publication.

### 27.3 Platform tree mismatch

Invalidate the release for certification. Do not execute A-cases.

### 27.4 Web normal Chat unavailable

Record `PLATFORM_LIMITATION/BLOCKED`.

Because Web normal Chat is release-blocking, the candidate cannot become `PRIVATE_PLUGIN_CERTIFIED`.

### 27.5 Resolver failure

Record the resolver observation separately from behavioral results.

Do not execute A06 through generic fallback ChatGPT behavior.

### 27.6 A06 failure

Stop the candidate before remaining A-cases.

### 27.7 Same-plugin update requires deletion

Stop and require an explicit new lifecycle decision rather than knowingly retaining stale files.

## 28. Testing strategy

Implementation uses TDD.

Required test classes include:

- canonical version authority and no stale SKILL version;
- portable manifest generation;
- official schema validation;
- OpenAI interface metadata generation;
- deterministic candidate build;
- deterministic distribution archive;
- archive root/no-wrapper enforcement;
- one-plugin archive enforcement;
- candidate/archive tree equivalence;
- transport-conditional installation evidence schema;
- S→P→M verification for local marketplace evidence;
- P→B→O verification for personal plugin evidence;
- platform tree mismatch rejection;
- surface-specific certification profile;
- no cross-surface PASS inheritance;
- no cross-transport PASS inheritance;
- personal plugin scope/discoverability enforcement;
- release-ID-bound acceptance;
- stale/foreign installation evidence rejection;
- archive inspector safety limits;
- CI distinction between HEAD reproducibility and frozen certification;
- regression preservation of Building/Blueprint P0 behavior.

Full repository CI must remain green before any Plugin Creator mutation.

## 29. Deployment mutation boundaries

The implementation plan must distinguish:

### Autonomous engineering actions

- branch-local code/docs/tests;
- deterministic local/CI builds;
- validation;
- evidence generation;
- draft PR updates.

### Explicitly gated external actions

Creating or updating the real personal plugin is an external mutation.

It may occur only after all static gates for the exact candidate are green and the implementation plan reaches the dedicated deployment task.

### Protected actions not authorized by this design

- merge;
- release/tag;
- Stable promotion;
- public publication;
- branch deletion;
- force-push rewriting historical branches.

## 30. Success criteria

SIM v0.2.3 architecture is successfully implemented only when all of the following are proven:

1. `production/sim/**` remains the sole handwritten runtime authority.
2. The canonical version is `0.2.3-preview` with no independent stale SKILL version.
3. P5 is deterministically reproducible.
4. Root `plugin.json` validates against the pinned official Agent Plugins schema.
5. B5 is a deterministic one-plugin archive whose tree equals P5.
6. Plugin Creator creates or validly updates a USER/PRIVATE plugin release O5.
7. Retrieved O5 content independently reconstructs exactly P5.
8. ChatGPT Web normal Chat resolves the exact O5 plugin release.
9. Fresh A06 passes on O5.
10. Fresh required Web acceptance passes on O5.
11. Required Desktop acceptance passes.
12. Required Codex acceptance passes.
13. No unresolved P0/P1 integrity or certification finding remains.
14. Final certification is derived, not asserted.
15. No historical acceptance result is reused across changed candidate/release/protocol identity.

Only then may the release state become:

`PRIVATE_PLUGIN_CERTIFIED`

## 31. Architectural decisions summary

The approved v0.2.3 direction is:

- **native plugin**, not Custom GPT;
- **skills-only**, no unnecessary MCP;
- **USER / PRIVATE** OpenAI personal plugin;
- **GitHub canonical source**;
- **deterministic portable package** as the deployable artifact;
- **Plugin Creator** as production deployment transport;
- **local marketplace** only for development/diagnostics;
- **ChatGPT Web normal Chat** as mandatory release-blocking surface;
- **Desktop and Codex** as additional required surfaces;
- **exact release-bound evidence** with no inherited live PASS across identity changes.

This is a deployment/certification architecture evolution, not a SIM product rewrite.
